# Compute Cluster — веб-застосування для трудомістких обчислень з балансуванням навантаження

Задачі (на вибір користувача): **розв'язування СЛАР** (метод Гауса), **метод скінченних елементів**
(рівняння Пуассона на трикутній P1-сітці + CG), **обробка зображень** (множина Мандельброта).

## Архітектура

```
                  HTTPS :8443
 Браузер ───────────────────────►  nginx  (load balancer, TLS)
                                      │  round-robin по DNS-імені "app"
                        ┌─────────────┼──────────────┐
                        ▼             ▼              ▼
                   app (repl.1)  app (repl.2)   app-dyn-N  ◄── запускає autoscaler
                   FastAPI +     FastAPI +      (docker API, ≤ MAX_SERVERS)
                   worker        worker
                     │  │          │  │            │
                     │  └── кожна задача = окремий ОС-процес (multiprocessing, можна вбити)
                     └──────────────┴───────┬───────┘
                                            ▼
                              PostgreSQL (користувачі, задачі, прогрес,
                              черга, реєстр серверів, події)
```

* **Балансування (п. 5).** nginx розподіляє HTTP-запити між усіма контейнерами `app`
  (Docker DNS повертає їх усі; nginx оновлює адреси кожні 3 с → нові сервери підхоплюються автоматично,
  мертві виключаються через `proxy_next_upstream`). Стан не зберігається в пам'яті серверів —
  будь-який сервер обслуговує будь-якого клієнта (JWT + PostgreSQL).
  Балансується і **обчислювальне навантаження**: черга задач спільна, кожен сервер бере задачу
  лише коли має вільний слот (`SELECT … FOR UPDATE SKIP LOCKED`), тож задачі розподіляються між серверами
  за принципом «найменш завантажений». В інтерфейсі видно, який сервер відповів (`X-Served-By`) і який виконує задачу.
* **Обмеження трудомісткості (п. 1).** `limits.py`: діапазони параметрів (n ≤ 2500, сітка ≤ 300×300,
  ширина×висота×ітерації ≤ 4·10⁸ тощо) + жорсткий ліміт часу `MAX_TASK_SECONDS` (процес вбивається).
  Перевірка є на клієнті (миттєва, індикатор навантаження) і повторно на сервері (HTTP 422).
* **Прогрес (п. 2).** Процес задачі шле `(відсоток, етап)` батьківському воркеру → запис у БД →
  клієнт опитує `/api/tasks` щосекунди.
* **Історія / скасування / ліміти (п. 3).** Список задач користувача, деталі й результат, скасування
  (у черзі — одразу; виконувані — процес вбивається), видалення. Ліміти: ≤3 активних задач на користувача,
  ≤20 записів історії (старі автоматично видаляються), ≤50 задач у глобальній черзі.
* **Авторизація й HTTPS (п. 4).** Реєстрація/вхід, паролі — PBKDF2-SHA256 (200k ітерацій, сіль),
  сесія — JWT. nginx терміналює TLS (самопідписаний сертифікат генерується при старті), HTTP→HTTPS редирект.
* **Черга з ETA (п. 6).** Якщо вільних слотів немає, задача отримує статус «у черзі»; клієнт бачить позицію
  і орієнтовний час очікування (розраховується з кількості слотів і середньої тривалості задач цього типу).
* **Автомасштабування (п. 7).** Сервіс `autoscaler` через Docker API: є черга і слотів немає ≥5 с → запускає
  новий контейнер `app-dyn-*` (не більше `MAX_SERVERS=5`); простій ≥45 с → сервер переводиться в `draining`,
  дочекається завершення задач і зупиняється. Сервери з compose (2 шт.) не зупиняються.
* **Адмін-панель (п. 8).** `/admin.html` (користувач `admin`): сервери (онлайн/draining, слоти, CPU, RAM, uptime),
  усі активні процеси всіх користувачів з прогресом і кнопкою примусового скасування, останні завершені,
  журнал подій (старт/зупинка серверів, автоскейлінг, перепризначення задач).
* **Відмовостійкість.** Якщо сервер падає, через 15 с інші помічають відсутність heartbeat
  і повертають його задачі в чергу.

## Запуск

Потрібен Docker з Compose v2.

```bash
docker compose up --build
```

Відкрийте **https://localhost:8443** (браузер попередить про самопідписаний сертифікат — підтвердіть виняток).
Адміністратор: `admin` / `admin12345` (змініть через `ADMIN_PASSWORD`, `SECRET_KEY` у `.env`).

## Демонстрація балансування

1. Зареєструйтесь, запустіть кілька задач — у картках видно різні сервери-виконавці; за F5 змінюється «сервер, що відповів».
2. `pip install requests && python scripts/loadtest.py --users 6 --per-user 3` — 18 важких задач:
   4 слоти (2 сервери × 2) заповнюються, решта стає в чергу з ETA, через ~5 с автоскейлер додає сервери
   (до 5 всього), а після завершення — через ~45 с зупиняє зайві. Все це видно в `/admin.html`.
3. Відмовостійкість: `docker stop <контейнер app>` — задачі повертаються в чергу й виконуються іншим сервером.
4. Логи балансера: `docker compose logs -f nginx` (у кожному рядку видно `upstream`-адресу).

## Структура

```
docker-compose.yml          # db, app (×2), nginx, autoscaler
nginx/                      # load balancer + TLS
backend/app/main.py         # REST API, авторизація, адмін-API
backend/app/worker.py       # диспетчер: черга, процеси, прогрес, heartbeat, відновлення
backend/app/tasks.py        # алгоритми (Гаус, МСЕ, Мандельброт)
backend/app/limits.py       # обмеження трудомісткості + валідація
backend/static/             # frontend (index, admin)
autoscaler/                 # горизонтальне масштабування через Docker API
scripts/loadtest.py         # навантажувальний тест
```

## Примітки

* Автоскейлеру потрібен доступ до `/var/run/docker.sock` — це потужний привілей, для лабораторної роботи прийнятно.
* Для справжнього сертифіката замініть `10-gen-cert.sh` на Let's Encrypt або змонтуйте свої `server.crt/key`.
* Ліміти (`SERVER_CAPACITY`, `MAX_TASK_SECONDS`, `MAX_SERVERS` …) налаштовуються в `docker-compose.yml`.
